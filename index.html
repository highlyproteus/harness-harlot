Rust Mux

A reliability-first native terminal workspace whose PTYs and processes live in a persistent Rust service, independently of the restartable desktop UI.

Locked decisions

Session authority
The service owns PTYs, processes, session state, and layouts.
Desktop role
A native reconnectable client with workspaces, tabs, splits, and pane drag/drop.
Terminal engine
Alacritty's Rust terminal engine; no terminal emulator built from scratch.
First platforms
macOS and Linux; Windows is a documented later path.

System model

native GPU desktop → versioned local Unix-socket protocol → Tokio session service → local/SSH PTYs + canonical layout state. The desktop may disappear and reconnect without changing session ownership. GPUI is the first spike, not yet a framework lock.

Phases

  1. Foundation: source-informed architecture, process boundary, terminal-engine adapter, native GPU spike.
  2. Session core: Tokio daemon, framed local IPC, local PTYs, ordered streaming, reconnect semantics.
  3. Remote core: system OpenSSH in managed PTYs, standard SSH config, host-key and agent safety.
  4. Terminal: GPU-backed cells, input, Unicode, selection, scrollback, search.
  5. Workspace UX: tabs, split tree, pane drag/drop, atomic persistence.
  6. Reliability: local/SSH crash recovery plus macOS Spaces and Linux compositor soak testing.

Risks

Output pressure
A stalled client must never stall PTY reads or grow memory without bounds.
State races
Layout commands need revisions and deterministic conflict handling.
UI stalls
Terminal updates and display changes must stay off blocking IPC paths.
Recovery
Service crash recovery differs from desktop reconnect and must be stated honestly.

Deferred

No embedded browser, mobile app, generic remote-control UI, worktree or diff review, or AI-specific integrations. SSH terminal workspaces are early; optional remote rmuxd reattachment is later.
